# Rules and thresholds (v1)

All values are pedagogical, calibrated on the demo logs. In the code they are parameters, not hard-coded (see `minisoc/rules.py`).

| Rule | What it counts | Grouped by | Window | Threshold N |
|---|---|---|---|---|
| R1 SSH repeated failures | events ssh_auth_failure and ssh_invalid_user | source IP | 5 minutes, sliding | 5 |
| R2 HTTP errors | http_request with status 400 to 599 | source IP | 2 minutes, sliding | 5 |
| R3 Request spike | all http_request events | none (global) | 1 minute, fixed (calendar minute) | 30 |

## How a window works
- Sliding: for each IP, events are read in time order. If N or more fall within T minutes of each other, the rule fires.
- Fixed: events are counted per calendar minute (for example 14:08:00 to 14:08:59). Consecutive hot minutes are merged into one spike.
- Overlapping windows from the same IP are merged into one alert, from the first to the last event. One burst gives one alert, not many. Two bursts separated by more than the window give two alerts.

## Alert content (explicabilite)
Rule, title, priority, first and last event time, window, IP (empty for R3), event count, threshold, a details sentence, and the list of events that prove it (table alert_events).

## Priority
- Below the threshold: no alert. Single events keep their own severity (low or info).
- medium: the threshold is reached.
- high: the count is 2 x N or more, or the same IP triggers two different rules.
- R3 uses the busiest minute for this comparison, not the total of merged minutes.

## Scenarios (one per rule, plus under-threshold cases)
| Rule | File | Triggers | Under threshold, no alert |

| R3 | data/demo_r3_http.log | 45 requests in the minute 14:08 | 25 requests in the minute 14:05 |

## Expected results
- Demo v1 (29 events): 2 alerts, both high. R1 and R2 for 203.0.113.50, escalated because the same IP triggers two rules. No R3 alert (the busiest minute has 8 requests, below 30).
- With the R3 scenario also imported (123 events): a third alert, R3, priority medium, count 45.

## Scenario R3 (data/demo_r3_http.log)
Generated by `make_demo_r3.py`: 94 synthetic HTTP lines on 18 Nov 2026. Quiet minutes have 3 requests. The minute 14:05 has 25 requests (busy but below the threshold). The minute 14:08 has 45 requests, mostly from 198.51.100.10 (spike: 1 alert, priority medium).

## Known limit of R3
The window is fixed (calendar minute). A burst split across a minute boundary, such as 15 requests at 14:00:50 and 15 at 14:01:10, stays below the threshold in each minute and is missed. A sliding window would catch it, at the cost of a more complex explanation.
